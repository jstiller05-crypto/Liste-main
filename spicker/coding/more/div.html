<div>

Der bedeutungslose Block-Container: keine eigene Rolle, kein eigener Inhaltstyp – nur Layout, Styling und JS-Ansprechpunkt, wenn kein semantisches Element passt.

Verhalten im Layout

Als Block-Element (display: block) verhält sich ein <div> standardmäßig so:

  • Breite: nimmt die volle verfügbare Breite des Elternelements ein (nicht die Breite des Inhalts) – width wirkt und setzt diese Breite herab.
  • Höhe: richtet sich nach dem Inhalt. Ohne Inhalt und ohne min-height ist ein leeres <div> genau 0 Pixel hoch – es nimmt dann keinen sichtbaren Platz ein, selbst mit Border/Padding auf 0.
  • Umbruch: erzeugt vor und nach sich einen Zeilenumbruch – zwei <div>s stehen immer untereinander, nie nebeneinander (das ändert erst Flex/Grid/Float, siehe unten).
  • width/height wirken; bei display: inline (z. B. <span>) würden sie ignoriert.
Div A (margin-bottom: 20px)
Div B (margin-top: 12px)

Margin-Collapsing: Stehen zwei Block-Boxen direkt untereinander, verschmelzen ihre vertikalen Margins zum größeren der beiden Werte – nicht zur Summe. Im Beispiel oben ergibt margin-bottom: 20px + margin-top: 12px einen Abstand von 20px, nicht 32px.

Das passiert auch zwischen einem Container und seinem ersten bzw. letzten Kind, wenn kein border, padding, Abstand oder neuer Block Formatting Context dazwischenliegt: Der margin-top des ersten Kindes „wandert“ dann nach außen vor den Container. Das ist einer der häufigsten CSS-Überraschungsmomente.

Als CSS-Container

Ausführlich hier, weil <div> das typische Element dafür ist – alle anderen Container-Seiten verweisen auf diesen Abschnitt.

CSSWas passiert
display: flexDas <div> wird zum Flex-Container, seine direkten Kinder werden automatisch zu Flex-Items – float, clear und vertical-align wirken dann auf den Kindern nicht mehr (siehe Flexbox).
display: gridWird zum Grid-Container, Kinder werden zu Grid-Items, platziert nach grid-template-* (siehe Grid).
position: relativeWird zum Containing Block (Bezugsrahmen) für jedes Kind mit position: absolute – dessen top/left/… zählen dann ab diesem <div>, nicht ab der ganzen Seite (siehe position).
overflow: hidden/auto/scrollSchneidet überstehenden Inhalt ab bzw. macht scrollbar – erzeugt dabei als Nebeneffekt einen neuen Block Formatting Context (klassischer „Clearfix“ für Floats, siehe Box-Modell).
display: flow-rootErzeugt einen neuen Block Formatting Context gezielt, ohne die Nebeneffekte von overflow (kein Abschneiden, keine Scrollbar). Schließt darin enthaltene Floats vollständig ein – der modernere Clearfix-Ersatz.
container-type: inline-sizeMacht das <div> zum Query-Container: Kinder können mit @container (min-width: …) auf DESSEN Breite reagieren statt auf die des Browserfensters (Container Queries).

In JavaScript

Ausführlich hier – die anderen Container-Seiten verweisen darauf und nennen nur Besonderheiten.

const container = document.querySelector(".card-list");

// Suche NUR innerhalb des Containers (nicht auf der ganzen Seite)
const firstCard = container.querySelector(".card");

// children: nur Element-Kinder (HTMLCollection, live)
// childNodes: AUCH Text- und Kommentarknoten (NodeList, live)
console.log(container.children.length, container.childNodes.length);

// Inhalt setzen: sicherer/schneller als innerHTML bei dynamischen Daten
const card = document.createElement("div");
card.textContent = "Neue Karte";
container.append(card);                 // hängt an
container.replaceChildren(card);         // ersetzt ALLES im Container

Event-Delegation

Statt an jede einzelne Karte einen eigenen Listener zu hängen, reicht ein Listener auf dem Container. Das funktioniert auch für Karten, die erst später per JavaScript dazukommen:

container.addEventListener("click", function handleCardClick(event) {
  // closest() sucht ab dem Klick-Ziel nach OBEN nach einem ".card"
  // (auch wenn man z. B. auf ein  MITTEN in der Karte klickt)
  const card = event.target.closest(".card");
  if (!card) return;             // Klick war außerhalb einer Karte

  console.log("[delegation] Karte angeklickt, id:", card.dataset.id);
});

element.dataset liest data-*-Attribute: data-id="42" wird zu element.dataset.id === "42". element.closest(selector) prüft das Element selbst und dann jeden Vorfahren, bis einer passt oder nichts mehr übrig ist.

Barrierefreiheit & Semantik

  • Kein Landmark. Ein <div> taucht in der Landmark-Navigation von Screenreadern nicht auf (anders als <main>, <nav> …) – Nutzer können nicht gezielt zu ihm springen.
  • Die Rolle generic wird zwar in der Accessibility-API sichtbar gemacht (für Layout-Infos), hat aber keinen eigenen Namen. Laut ARIA-Spezifikation sind aria-label und aria-labelledby bei role="generic" eigentlich nicht zulässig – wer einem Container einen zugänglichen Namen geben will, nimmt besser eine passende Rolle wie role="group" oder ein semantisches Element.
  • Inhalt innerhalb eines <div> wird trotzdem normal vorgelesen – nur eben ohne Gruppierung oder Sprungmarke.
  • Suchmaschinen ziehen aus <div> keine strukturelle Bedeutung (anders als z. B. <article>).

Verschachtelung: erlaubt / verboten

✓ <div><div>…</div></div>              (jedes Flow-Content-Element darf div enthalten)
✓ <dl><div><dt>…</dt><dd>…</dd></div></dl>   (Sonderfall, siehe Steckbrief)

✗ <span><div>…</div></span>
  Ungültig nach Inhaltsmodell (span erlaubt nur Phrasing Content).
  ABER: Der Parser korrigiert hier NICHTS – das div landet trotzdem
  genau so verschachtelt im DOM, wie es im Quelltext steht. Ein
  Validator meldet den Fehler, der Browser rendert es trotzdem.

✗ <p>Text <div>…</div></p>
  Hier GREIFT der Parser ein: <p> hat eine Sonderregel ("implied
  end tag") und wird automatisch VOR dem <div> geschlossen.
  Im DOM-Inspektor stehen <p> und <div> als GESCHWISTER,
  nicht verschachtelt – anders als im Quelltext!

✗ <select><div>…</div></select>
  select erlaubt nur <option>/<optgroup> – div wird hier
  nicht wie gewünscht angezeigt.

Typische Fehler

  • „div-Suppe“: viele bedeutungslose, verschachtelte <div>s statt semantischer Elemente – schwerer zu lesen UND keine Landmarks für Screenreader.
  • Klickbares <div> statt <button>: ohne tabindex="0", role="button" und eigenem keydown-Handler für Enter/Leertaste ist es per Tastatur nicht bedienbar und für Screenreader nicht als Button erkennbar.
  • aria-label auf einem bedeutungslosen <div> in der Annahme, es werde wie eine Landmark vorgelesen – die Rolle bleibt generic, viele Screenreader ignorieren den Namen trotzdem (siehe oben).
  • Margin-Collapsing-Überraschung: unerwarteter Abstand ÜBER einem Container, weil der margin-top des ersten Kindes nach außen „durchgereicht“ wird.
  • overflow: hidden nur für den Clearfix-Effekt gesetzt – dabei wird oft versehentlich Inhalt abgeschnitten, der eigentlich über den Rand ragen sollte (z. B. ein Tooltip). Besser gezielt display: flow-root nutzen.
