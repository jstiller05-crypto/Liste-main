Module, venv & pip

Code mit import wiederverwenden, eigene Module schreiben und fremde Pakete sauber installieren – auf Arch mit venv oder pacman statt systemweitem pip.

Was ist das?

Ein Modul ist eine .py-Datei, deren Funktionen und Klassen man in anderen Dateien mit import benutzt. Ein Paket ist eine Sammlung von Modulen. Viele sind schon dabei (Standardbibliothek: math, random, json …), weitere holt man mit pip von PyPI, dem Python-Paketverzeichnis.

import

# imports.py
import math                         # ganzes Modul – Zugriff mit math.
print(math.sqrt(16), math.pi)

import random as rnd                # mit Kurznamen
print(rnd.randint(1, 6))            # Würfel: 1 bis 6

from datetime import date           # nur einen Namen holen – ohne Präfix nutzbar
print(date.today())

from pathlib import Path, PurePath  # mehrere Namen

import sys
print(sys.version)                  # Python-Version
print(sys.argv)                     # Argumente von der Kommandozeile
python imports.py eins zwei

from modul import * holt alles auf einmal – vermeiden: Man sieht dann nicht mehr, woher ein Name kommt.

Eigene Module

Zwei Dateien im selben Ordner. Der Modulname ist der Dateiname ohne .py.

# geometry.py
"""Kleine Hilfsfunktionen für Flächen."""

PI = 3.14159

def circle_area(radius):
    return PI * radius ** 2

def rectangle_area(width, height):
    return width * height
# main.py
import geometry
from geometry import rectangle_area

print(geometry.circle_area(2))
print(rectangle_area(3, 4))
python main.py

if __name__ == "__main__"

Beim import führt Python die ganze Datei einmal aus – auch Test-Ausgaben ganz unten. Die Variable __name__ verrät, wie die Datei gestartet wurde: direkt mit python datei.py heißt sie "__main__", bei einem Import trägt sie den Modulnamen.

# temperature.py
def to_fahrenheit(celsius):
    return celsius * 9 / 5 + 32

def main():
    print("20 °C sind", to_fahrenheit(20), "°F")

if __name__ == "__main__":      # nur beim direkten Start, NICHT beim Import
    main()
python temperature.py                                      # ruft main() auf
python -c "import temperature; print(temperature.to_fahrenheit(0))"   # nur die Funktion, ohne main()

Entspricht der main()-Funktion in C++: ein klarer Startpunkt, der Rest der Datei bleibt wiederverwendbar.

Arch: „externally-managed-environment“

Wer auf Arch einfach pip install requests tippt, bekommt:

error: externally-managed-environment

× This environment is externally managed
╰─> To install Python packages system-wide, try 'pacman -S python-xyz' …

Warum? Das System-Python gehört pacman. Viele Arch-Programme sind in Python geschrieben und brauchen bestimmte Paket-Versionen. Würde pip dort Dateien überschreiben, die pacman verwaltet, könnten Systemprogramme kaputtgehen – und pacman wüsste nichts davon. Darum verweigert pip das (Regel „PEP 668“).

SituationRichtige WahlBefehl
Eigenes Projekt mit Paketenvenv – eigene Umgebung nur für dieses Projektpython -m venv .venv
Paket für kleine Skripte überall auf dem System, und es gibt ein Arch-Paketpacman – wird mit dem System aktuell gehaltensudo pacman -S python-requests
Ein fertiges Python-Programm (z. B. yt-dlp, black)zuerst pacman; sonst pipx (eigenes venv je Programm)sudo pacman -S python-pipx, dann pipx install name

Arch-Pakete für Python heißen fast immer python-<name>. Suchen mit pacman -Ss python-requests (-Ss = in den Paketquellen suchen).

Nicht benutzen: pip install --break-system-packages und sudo pip install. Beide schalten genau den Schutz ab, der das System heil hält.

venv – virtuelle Umgebung

Ein venv ist ein Ordner (üblich: .venv) mit einem eigenen python und eigenem pip. Pakete landen nur dort. Jedes Projekt bekommt sein eigenes – so stören sich Versionen nicht, und Löschen des Ordners räumt alles auf.

cd ~/Dev/projects/mein-projekt     # in den Projektordner wechseln
python -m venv .venv               # venv im Unterordner .venv anlegen (einmalig)

# aktivieren – je nach Shell (echo $SHELL zeigt, welche man hat)
source .venv/bin/activate          # bash / zsh
source .venv/bin/activate.fish     # fish

which python                       # zeigt jetzt …/mein-projekt/.venv/bin/python
pip install requests               # landet NUR im venv – kein Fehler mehr
python main.py                     # nutzt die Pakete aus dem venv

deactivate                         # venv wieder verlassen

Ist ein venv aktiv, steht meist (.venv) vorn in der Eingabezeile. Ohne Aktivieren geht es auch – das python des venv direkt aufrufen: .venv/bin/python main.py.

Der Ordner .venv gehört nicht ins Git-Repository: in .gitignore die Zeile .venv/ eintragen.

Tipps & typische Fehler

  • ModuleNotFoundError: No module named 'requests' – das Paket fehlt in dieser Umgebung. Fast immer ist das venv nicht aktiv. Mit which python prüfen.
  • Die eigene Datei nicht wie ein Modul nennen (random.py, requests.py) – import findet zuerst die eigene Datei.
  • Ein venv nicht verschieben oder umbenennen – es merkt sich absolute Pfade. Lieber löschen (rm -r .venv) und neu anlegen; requirements.txt bringt die Pakete zurück.
  • Nach einem großen Python-Update durch pacman (z. B. 3.13 → 3.14) funktionieren alte venvs nicht mehr – ebenfalls neu anlegen.
  • Fehlt pip außerhalb eines venv: Das ist auf Arch normal, es steckt im Paket python-pip. Im venv ist pip immer dabei.
  • Importe stehen ganz oben in der Datei: erst Standardbibliothek, dann fremde Pakete, dann eigene Module.
