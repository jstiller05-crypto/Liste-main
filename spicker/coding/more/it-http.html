HTTP

HTTP (HyperText Transfer Protocol) ist das Protokoll, über das Browser und Server im Web kommunizieren: Der Browser schickt eine Request (Anfrage), der Server antwortet mit einer Response.

HTTPS

HTTPS ist HTTP, zusätzlich verschlüsselt über TLS/SSL (siehe Verschlüsselung im Sicherheits-Teil des Spickers). Inhalt und Adresse der Anfrage sind dadurch unterwegs nicht im Klartext mitlesbar. Heute ist HTTPS praktisch Standard, selbst für Seiten ohne Login.

Request & Response

Eine Request besteht aus Methode + Pfad, Headern und optional einem Body (z. B. Formulardaten). Eine Response besteht aus Statuscode, Headern und optional einem Body (z. B. HTML oder JSON). Im Spicker selbst nutzt fetch genau dieses Muster, um mit dem Node-Server zu sprechen.

Wie man GET und POST konkret mit fetch in JavaScript auslöst und wie app.get/app.post sie in Express entgegennehmen, steht bereits bei Node.js im Spicker.

Statuscodes

Jede Response trägt einen dreistelligen Statuscode, der auf einen Blick zeigt, wie die Anfrage gelaufen ist:

CodeBedeutung
200OK – alles erfolgreich
201Created – erfolgreich neu angelegt
204No Content – erfolgreich, aber kein Inhalt in der Antwort
301Moved Permanently – dauerhaft umgezogen
302Found – vorübergehend woanders
304Not Modified – unverändert, Browser-Cache nutzen
400Bad Request – Anfrage fehlerhaft
401Unauthorized – Anmeldung fehlt
403Forbidden – Zugriff verboten (auch angemeldet)
404Not Found – nichts unter dieser Adresse
500Internal Server Error – Fehler beim Server selbst
502Bad Gateway – Server hat vom Vorgelagerten ungültige Antwort bekommen
503Service Unavailable – Server gerade überlastet/nicht bereit
Grobe Faustregel an der ersten Ziffer: 2xx = erfolgreich, 3xx = Weiterleitung, 4xx = Fehler beim Client, 5xx = Fehler beim Server. Der eigene Node-Server dieses Spickers (server.js) nutzt genau diese Codes: 301 für alte Adressen, 404 für unbekannte Dateien, 500 bei internen Fehlern.

Header

Header sind Zusatzinformationen VOR dem eigentlichen Inhalt einer Request oder Response – als Schlüssel-Wert-Paare, z. B. Content-Type: application/json (welches Format der Body hat) oder Content-Length (wie groß der Body ist).

Cookie

Ein Cookie ist ein kleines Stück Daten, das der Server per Header beim Browser ablegt und das der Browser bei weiteren Anfragen an DENSELBEN Server automatisch mitschickt. Damit „erinnert“ sich der Server über mehrere Anfragen hinweg an denselben Client – z. B. für einen Login-Zustand, obwohl HTTP selbst eigentlich zustandslos ist.

REST-API

Eine REST-API ist eine gängige Bauweise für Web-Schnittstellen: Jede Ressource bekommt eine eigene Adresse (URL), und HTTP-Methoden bestimmen die Aktion darauf – z. B. GET /api/progress zum Abrufen, PUT /api/progress/coding/a.html zum Ändern, genau wie es die eigene API dieses Spickers macht.

JSON über HTTP

Für den Datenaustausch zwischen Client und Server hat sich JSON (siehe JS-Teil des Spickers) als Standardformat durchgesetzt: kompakt, von praktisch jeder Sprache lesbar. Der Header Content-Type: application/json sagt dem Empfänger, dass der Body im JSON-Format vorliegt.

Tipps & typische Fehler

  • GET-Anfragen sollten NIE Daten verändern – Browser, Proxys und Suchmaschinen gehen bei GET grundsätzlich davon aus, dass es gefahrlos wiederholbar ist.
  • 401 (nicht angemeldet) und 403 (angemeldet, aber nicht erlaubt) werden oft verwechselt – es sind zwei unterschiedliche Situationen.
  • „Es kommt nichts zurück“ bei fetch ist fast immer im Network-Tab der Browser-Entwicklertools sichtbar – Statuscode und Response dort zuerst prüfen, bevor man im Code sucht.
