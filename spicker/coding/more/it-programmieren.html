Quellcode

Der Quellcode ist der von Menschen geschriebene, lesbare Programmtext in einer Programmiersprache – bevor er in irgendeiner Form ausgeführt wird.

.cpp.js.lua

Syntax vs. Semantik

Syntax sind die formalen Regeln, WIE Code geschrieben werden muss (die „Grammatik“ einer Sprache). Semantik ist, WAS der Code tatsächlich bedeutet bzw. bewirkt. Syntaktisch fehlerfreier Code kann trotzdem die falsche Semantik haben – er tut dann einfach nicht das Gewollte, ohne dass die Sprache sich beschwert.

JIT

Ein JIT-Compiler (Just-In-Time) übersetzt Code ERST zur Laufzeit – aber, anders als ein reiner Interpreter, in ECHTEN Maschinencode, meist nur für die Teile, die wirklich oft durchlaufen werden („hot code“). Das ist ein Kompromiss zwischen schnellem Start und schneller Ausführung.

Hochsprache vs. Maschinensprache

Die Maschinensprache sind die rohen Bytes, die eine CPU direkt versteht. Eine Hochsprache ist für Menschen lesbar und deutlich abstrakter – sie muss erst (per Compiler, Interpreter oder JIT) in Maschinensprache überführt werden, bevor die CPU etwas damit anfangen kann.

statisch vs. dynamisch typisiert

Bei statischer Typisierung steht der Typ einer Variable schon beim Schreiben/Kompilieren fest und wird VOR der Ausführung geprüft – Typfehler fallen früh auf. Bei dynamischer Typisierung wird der Typ erst zur Laufzeit anhand des aktuellen Werts bestimmt.

Bibliothek vs. Framework

Eine Bibliothek ist eine Sammlung fertiger Funktionen, die DU in deinem Code aufrufst – du behältst die Kontrolle über den Ablauf. Ein Framework gibt die Grundstruktur des Programms vor und ruft stattdessen DEINEN Code auf („Inversion of Control“).

API

Eine API (Application Programming Interface) ist eine Schnittstelle, über die ein Programm, eine Bibliothek oder ein Dienst kontrolliert genutzt werden kann, ohne die inneren Details zu kennen – von einzelnen Funktionen einer Bibliothek bis zur Web-API dieses Spickers (siehe REST-API im Protokolle-Teil).

Eine IDE (Integrated Development Environment) bündelt Editor, Compiler-/Interpreter-Anbindung, Debugger und mehr in EINER Oberfläche.

Tipps & typische Fehler

  • „Mein Code läuft nicht, aber es gibt keinen Fehler“ ist oft ein Semantik-Problem – syntaktisch korrekt, aber nicht das Gewollte.
  • Dynamisch typisierte Sprachen fangen Typfehler oft erst zur Laufzeit ab, mitten in der Ausführung – gründliches Testen wird dadurch wichtiger.
  • „Bibliothek einbinden“ reicht oft nicht – manche brauchen zusätzlich einen Paketmanager-Befehl (z. B. npm install), um überhaupt vorhanden zu sein.
